Asked for: a proper preview image when the GitHub Pages link is pasted into WhatsApp, Messenger, X, Bluesky or Discord, matching the Figma listing's thumbnail and description. It had none — the URL shared as bare text.

**Link preview card built** — [[decision-link-preview-card]]. `public/og-image.jpg` is `figma/brand/cover-1920x1080.png` centre-cropped to 1200x630 and encoded at JPEG 0.92, by a new `scripts/make-og-image.mjs` modelled on `make-favicons.mjs`. Both transforms measured rather than assumed: the same frame is 884 KB as PNG against 79 KB as JPEG, and the 36px trimmed off each of the top and bottom takes only backdrop. The copy is the sentence already in `figma/brand/listing.md` and the manifest, so the listing and a pasted link now show the same face.

The one real trap: **the Open Graph URLs cannot use `%BASE_URL%`.** Every other URL in `index.html` is relative because `base` flips between three values, and that is right for a browser, which resolves against the document it just loaded. A scraper never loads the document — it reads `og:image` and fetches that string — and most of them, WhatsApp and Discord included, will not resolve a relative path. The failure is a card with text and no picture, on exactly the platforms this was for, with nothing broken anywhere you would look. `vite.config.js` gained a `%SITE_URL%` token filled by a `transformIndexHtml` hook off the same `base` expression.

**Then: how to test it before pushing live.** Three rungs, written up in the decision note. `bun run preview:card` is the offline one — it checks the built artifact (absolute URLs, image present, declared dimensions matching the JPEG's real SOF values, byte size in the reliable range), exits non-zero, and now runs in the deploy job too. It also renders a mock of the three card framings so the crop and the truncation can be eyeballed without deploying. Above that, `SITE_URL=` overrides the computed origin so a tunnel can be pointed at real scrapers without touching the live site, and `bun run deploy:dev` publishes to the `/dev/` channel, which `gh-pages -e dev` scopes safely away from production.

Worth remembering: scrapers cache by exact URL, WhatsApp for about a week, so a throwaway `?v=2` is how you retest without waiting.

## Bun 1.4

Released 14:07 UTC today; asked whether to move. The answer turned out to be that we already had — both CI jobs said `bun-version: latest`, so the next push would have built on a two-hour-old major with nothing here on the same version to reproduce a failure. Pinned both to `1.4.0` and upgraded the local toolchain from 1.3.11 to match. Write-up in [[decision-pin-bun-version-in-ci]].

Bun's surface here is narrow enough that the release notes barely apply: it installs packages and runs scripts, and everything it launches — vite, tsc, eslint, Playwright — goes to Node 22 through its own shebang. The whole "Upgrading to 1.4" list misses the project.

The interesting bit was the lockfile. 1.4 writes new lockfiles as `lockfileVersion: 2` and the notes say to run `bun install` to migrate, which reads like a one-way door — once migrated, bun 1.3 can't read it. It doesn't migrate. `bun install` said no changes; `bun install --lockfile-only`, which forces a full rewrite, produced a byte-identical file still on v1. The `configVersion: 0` field pins the old defaults the same way, which is also why `node_modules` kept the hoisted layout instead of flipping to 1.4's isolated linker. So: no diff, and `bun.lock` is still backward-compatible. Saved to global memory, since nothing about it is specific to this repo.

Ladder clean on 1.4.0 — lint, typecheck, both builds, `preview:card`, 39/39 specs. Checked the thing CLAUDE.md warns about specifically: `GITHUB_PAGES=1 vite build` in POSIX inline form still works under bun's shell on Windows.
