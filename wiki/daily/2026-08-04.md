## Saved grows in banks

Issue [#64](https://github.com/redlamp/color-taylor/issues/64) resolved. Saved holds 12, adds a row when free slots drop to 3, caps at 36. Full rationale in [[decision-saved-grows-in-banks]].

Researched the alternatives first, since the question was "how would you approach this" rather than "build this": Procreate uses named palettes of 30 in a scrolling list, Illustrator uses swatch groups as folders, Photoshop has no grouping at all, and Figma's picker has **no user-curated swatch grid whatsoever** - Document colors are auto-collected and Libraries are published named styles. That last one is worth remembering twice over: it sets the ceiling for how far this should scale, and a curated ad-hoc grid is a genuine gap in Figma's picker, which helps the positioning question in [[plan-figma-plugin-release]].

The user's call was auto-grow rather than a manual "add 12" control, which is better - no control to explain and nothing to click.

Verified: seeded state stays at 12 (9 filled, 3 free - deliberately un-fitted, see the note), first save grows to 24, the twelfth grows to 36, ceiling holds at 36/34 in 6 rows at the narrow breakpoint. Clear returns to one bank.

The Saved sort control moved from `headerLeft` to the front of `headerRight`, so it leads Defaults and Clear instead of sitting opposite them. It reads rather than destroys, which is why it goes first in that group.

## Header hit area

The user reported the clickable part of the Recent/Saved headers being smaller than the header looks. Measured it: horizontally it was already full width (456 of 456), so the dead zone was **vertical** - the row was only as tall as its own content, leaving the section's top padding inert even though it reads as part of the header.

Fixed by pulling the hit area back over that padding with a negative margin plus matching padding, in both the flush and card variants. Header is now 40px tall in the panel, starts 1px below the section rule, and the action buttons still don't toggle the section.

Worth noting the general shape of that bug: a hit area that stops at the content box while the *visual* affordance includes the container's padding. Nothing looks wrong in a screenshot, and it only shows up when you click.

**Second half of it, found later by checking the app rather than only the plugin.** Recent's header still did not respond in its top band while Saved's did - same component, same variant, identical computed geometry. The hexagon's SVG box is 512px against a 436px stage, so it overhangs the next section by exactly 10px: the same band the negative margin had just claimed. The SVG is absolutely positioned and the header is in normal flow, so the SVG won the hit test and the header only *looked* clickable there.

Fixed with `relative z-10` on the header. Checked the hexagon did not lose reach in the trade - the SVG still owns everything through the stage and 4px past it; the header only wins where it overlaps the card below.

The lesson is about verification, not CSS: the plugin passed this test cleanly and the app did not, because only the app stacks the hexagon directly above these sections. Verifying the shared component on one surface was not enough.

## Grow threshold revised, and fixed control widths

Follow-up in the same session: grow when the **last free slot** fills, not at 3 free. Side benefit - the seed (9 of 12) is no longer sitting on the threshold, so `defaultSaved()` runs through `fitSaved()` like everything else and the special case is gone.

Sort/Defaults/Clear now hold a width instead of tracking their content. Measured both surfaces first, which is what made the answer non-obvious: `Sort: Bright` is 72px in the plugin (Inter 11px) but 98px in the app (Barlow), and `Defaults` is 57 vs 74. One shared width would have forced the plugin's Sort to 98px, which at the 300px minimum panel width leaves the section title nowhere to go. So narrow hosts get the tighter pair, keyed off `iconActions` - a prop that already means "this host is short on room".

**The trap:** `figma.css` already had `[data-armed] { min-width: 44px }` from an earlier pass at this same jitter. It is unlayered, so it beat the new 48px floor on specificity and the button got *narrower* on arming - the exact jump it was added to prevent. Removed the min-width, kept the color.

## Drag affordances

Drop a saved color on the trash to delete it (danger-colored ring, scales up on hover). The subtle part is marking the drop handled: `onDragEnd`'s drop-outside path would otherwise delete a *second* time, and by then the indices have shifted so it would take a different color with it.

Drag a Recent color onto a Saved slot to copy it in. Recent keeps its own - it is a log of where you have been and should not lose an entry because you filed it somewhere. Insert-between zones are suppressed for these: a Recent color has no position in Saved to slide out of, so every drop is "put it in this slot".

On touch, releasing over the trash already deleted (it takes the drop-outside path), so the outcome matches; only the hover cue is desktop-only.

Verified in the built panel: trash drop takes saved 9 to 8 and leaves Recent alone; Recent drag takes saved 8 to 9, leaves Recent at 2, and the target slot holds the dragged hex.
